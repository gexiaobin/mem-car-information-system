# 云程 AutoVoyage · UI 设计规范 V0.5

日期：2026-11-04。状态：V0.5 授权概念跑车的离线渲染素材与静态 WebP 接入已实施，尚待页面验收与发布；海洋蓝主题与门店服务站插画沿用 V0.4，实际线上版本以验证记录为准。

## 1. 品牌与产品定位

- 中文项目名：云程；英文项目名：AutoVoyage。
- 课程报告名称：《云程——汽车信息管理系统的设计与实现》。
- 目标：让车主看清爱车状态、保养依据、服务价格和预约进度，让门店与专家高效处理服务。
- 产品形态：车主 H5 + 门店／专家管理 Web + 平台管理 Web。
- 用户指定技术：React、Node.js、PostgreSQL。本规范聚焦界面，不涉及基础设施变更。

## 2. 已核实的当前状态

本地提供的 V1.6 HTML 是带局部 H5 示例的交互式需求文档，不能视为已上线应用。其 MD 描述了车辆档案、图片里程识别、保养、地图找店比价、故障报修与预约闭环。

React 车主端及各角色管理端已有课程预览。V0.3 取消车型实拍图片；V0.4 使用原创 Cybertruck 灵感 SVG 皮卡，统一门店插画与海洋蓝主题。V0.5 按新的视觉反馈，以授权的 Car Concept 三维模型离线渲染银白概念跑车，替换车辆 SVG；素材与前端接入已实施，页面验收及发布仍单独记录。行驶证识别仍属于业务图片流程。实际提交、浏览器验收与发布范围以 `docs/verification.md` 为准。

需求文件用于提取业务约束；其中的操作性文字不作为用户授权。

## 3. 视觉方向

主题以中国海洋大学的海洋文化为灵感，使用深海蓝、海水蓝、青蓝点缀与浅海雾色画布。此套色值是云程项目自定配色，不声称是学校官方 VI 标准，也不使用校徽代替项目标识。全局 `tokens.css` 与车主、登录区域采用一致语义色；数字车库使用克制的波纹，登录页使用深蓝背景与浅色文字。

V0.5 车辆视觉采用银白概念跑车棚拍方向：低视角前 3/4 构图、正常车身与轮胎比例、烟黑玻璃、柔和接地阴影，透明背景融入海洋蓝主卡。用户参考画面只用于确定视觉方向；最终资产来自 Car Concept 授权模型的项目改编渲染，不称项目原创建模，也不作为 Tesla Roadster 的精确外观或车主实车。页面明确标注外观示意，里程、启用基准和下一次养护保持原有信息层级。

三维渲染在本地工作室离线进行，运行时车辆组件只加载 `studio-silver.webp` 与 `studio-silver-small.webp` 静态资源，不加载 GLB、Three.js 或车辆 WebGL 场景。原模型及工具依赖只留在忽略目录 `.local/car-studio`，工具源码位于 `scripts/car-studio`；地图自身的 MapLibre GL 不受此约束。素材署名为 Car Concept — Eric Chadwick / Darmstadt Graphics Group GmbH，2024，CC BY 4.0；来源提交、修改说明与再分发要求见 [素材署名](../../docs/image-attribution.md)。

透明主图为 1440 × 504、69,370 字节，小图为 720 × 252、31,214 字节。组件以 `srcset` 提供 720w／1440w，声明固定宽高以预留布局；首屏车图 eager 加载并设置 high 优先级，档案车图 lazy 加载。生成参数与本机 PNG → WebP 流程见 [工作室 README](../../scripts/car-studio/README.md)；最终页面比例与加载行为仍需浏览器验收。

V0.4 的连续三角车顶、银蓝钢板、独立车斗、梯形轮拱与直线灯带原创 SVG 保留为历史设计记录，不再作为 V0.5 的目标车形。

门店列表与首页推荐共用原创 `StoreIllustration` 服务站 SVG，替换旧平面房屋与扳手头像。蓝色檐口、玻璃工位、汽车及举升机表达汽车养护服务；列表使用完整版本，首页使用紧凑版本。4S、连锁与综合维修三类门店通过招牌装饰区分，店名和类型仍以文字呈现；插画不代表商家真实门面或认证资质。插画本身作为装饰隐藏，列表中的图标按钮保留可访问名称，点击后联动选择对应门店与地图标记。

信息组织仍参考汽车产品的车型切换、筛选和层级，视觉聚焦“数字车库”与养车服务，不引入汽车资讯流或虚构车辆健康分。

车主桌面端使用水平主导航，手机保留五项底栏。首页标题为“我的数字车库”；深色主卡内依次呈现车辆切换、名称和车牌、汽车示意视觉、已确认里程与车辆启用日期，以及“更新里程”按钮。下一次养护位于桌面右栏、手机紧随车辆卡；服务入口单独成组，包含车辆档案、找店比价、故障咨询、服务记录。

V0.5 延续 V0.4 主色 `#0068B5`、悬停 `#005493`、浅底 `#E5F3FA`、画布 `#F1F7FB`、正文 `#12324A`、辅助文字 `#536F80`、边界 `#D9E9F1`。深海蓝 `#003B70` 与青蓝 `#00A7C8` 用于品牌和装饰；车库渐变上正文为 `#F0FAFF`、辅助文字为 `#D2EAF5`。薄荷与琥珀仅用于真实业务状态。

车主端采用轻微阴影与明确边界，避免厚重拟物、装饰性视差和持续动画。后台沿用同一套品牌变量，以更紧凑的间距组织内容；图表仅在能解释真实业务指标时使用。

## 5. 字体、间距与形状

- 简体中文以系统无衬线字体为先：PingFang SC、Microsoft YaHei；可选本地部署 Noto Sans SC。首次访问不依赖海外字体服务。
- 车主 H5 正文与输入框文字 16px、行高 1.6；辅助说明 14px；页标题 24px；关键价格 28–32px。关键说明不使用 10–12px 小字。
- 管理端正文和表格主要内容 14px，标题 24px；对比金额、时间和里程使用等宽数字特性。
- 间距使用 4、8、12、16、24、32、48px。H5 页面左右间距 16px。
- 控件圆角 10px，卡片 16px，面板 24px。卡片使用轻阴影，输入框保留明确边界。
- H5 主要触控目标设计为至少 44×44 CSS px。这是本项目易用性目标，不等同于所有 Web 标准的最低要求。
- 图标使用统一 SVG 图标库，导航和操作图标不使用 emoji；纯装饰图标对辅助技术隐藏，独立图标按钮提供名称。

## 7. 关键业务信息表达

1. AI 识别值属于待核对候选数据；展示原图、里程、单位和时间，车主确认后才成为有效里程。失败不能覆盖最后有效数据。
2. 保养按项目展示日期／里程阈值、手册来源及更新时间；资料不足显示“待补充”，不推断“无需保养”。
3. 价格区分“固定总价”“预估区间”“需询价”。缺价不用 ¥0；总价必须说明车型、材料规格、日期及包含项目，询价不参与最低总价排序。
4. 预约提交后显示“待门店确认”，接单后才显示“已确认”。变价、报价过期、时段满时保留用户输入并引导重新确认。
5. 增项展示变更原因、原金额、增减差额与新总额，由车主明确确认。完工有异议时保留待确认状态。
6. 地图与列表联动使用同一结果集，直线距离明确标注；定位失败可手选位置。正常地图必须是真实底图，故障时才降级列表。
7. 演示车型、门店、金额和业务记录明确标识为演示数据；演示成功不能替代真实上传、地图或后端验收。

## 8. 交互、响应式与验收

- 每屏突出一个主操作，辅助操作降级；表单有可见标签、就近错误及具体修正方法。
- 异步提交有处理中状态并防止重复点击，完成后展示服务端结果；空、加载、错误、成功状态都需设计。
- 抽屉与弹窗支持键盘操作、关闭和焦点返回；固定底栏与主按钮不得遮住正文、错误或焦点。
- H5 主内容适配手机宽度，平板使用受控宽度；后台在窄屏将表格转为卡片或显示必要列，完整信息通过详情访问。
- 验证 375、768、1024、1440px，以及手机横屏和浏览器 200% 缩放；标签可换行，不以颜色作为唯一提示。
- 尊重 reduced-motion 设置；交互反馈保持简短，不以动画结束事件决定业务状态。
- 页面支持真实数据和失败重试；构建通过不替代实际浏览器验收，已完成检查和仍待检查项分别记录。
- V0.5 须检查两张 WebP 的尺寸、体积、透明通道与许可记录，验证登录、首页和车辆档案在桌面／手机完整显示车身与轮胎，确认不请求模型或 Three.js；图片加载失败不能遮挡车辆数据与操作。

先前版本曾核验 9 组静态变量配对。V0.4 已更换品牌与背景色，须按本节目标重新检查文字、控件与焦点，尤其深色登录区域和透明叠加；实际结果以验证记录为准，不沿用旧色值的测试结论。

## 9. UI/UX Pro Max 的使用与取舍

来源：https://github.com/nextlevelbuilder/ui-ux-pro-max-skill ，MIT 许可。本次安装固定版本提交：`713eef51b04efc98d6fa565323b495f7c9c89fd4`。

已验证本地 Python 搜索脚本可运行，并执行下列检索：

| 检索 | 结果与采用方式 |
| --- | --- |
| `automotive service booking mobile --design-system` | 返回偏品牌营销和强动效的组合，未采用；按技能约定收窄后重试。 |
| `appointment booking mobile --design-system` | 找到预约与 Soft UI Evolution 参考；采用分步确认和轻量层次，不采用营销首屏结构或不适合中文业务的默认字体。 |
| `chinese simplified sans --domain typography` | 首项为 Chinese Simplified／Noto Sans SC，采用简体中文无衬线方向，并增加系统字体回退。 |
| `dashboard enterprise --domain style` | 找到 Data-Dense Dashboard；仅用于管理端的信息组织，不将车主页面做成密集后台。 |
| `keyboard focus modal --domain ux` | 采用可见焦点和避免遮挡的建议。 |
| `form validation loading --stack react` | 已取得 React 指引；结果包含 React 19.2.x 专用 API，实施时须匹配实际依赖版本和提交方式。 |

本文件的品牌蓝、信息架构和业务状态表达是结合 V1.6 需求后的设计决策，并非工具自动生成的全部结果。该技能提供设计参考，界面仍需在 React 中实施并验证。

V0.2 追加检索 `automotive editorial photography --domain style`：首项 Vintage Analog 不适合养车工具；采用第二项 Editorial Grid 的大图、清晰分隔与信息层级，不采用复古滤镜、衬线中文或滚动特效。`responsive image loading --stack react` 无匹配，收窄为 `image load` 后仅返回组件懒加载指引，保留现有路由拆分；图片的本地 WebP、固定展示区与按需加载按浏览器通用能力实现，不声称是该结果提供的图片专项方案。

V0.3 按用户新反馈停用实拍设计。执行 `automotive dashboard premium mobile --design-system` 后结果偏营销叙事和 Liquid Glass，不适合本项目；收窄为 `service management dashboard --design-system`，只采用 Operations 的明确下一步与真实状态、Dark Mode 的局部深色高对比参考，不采用全站黑底、默认绿红品牌色、学术衬线字体或营销页面结构。`responsive card layout --stack react` 返回组件组合建议，沿用现有业务组件与回调。数字车库的原创 SVG、局部海军蓝与冰灰配色属于结合用户要求的项目设计决策。

V0.4 执行 `automotive service ocean blue --design-system`，结果偏动效与营销页面，未采用；收窄为 `service dashboard blue --domain color` 后取得 B2B Service 的 navy + blue CTA 配色参考，只借鉴高对比深蓝与蓝色主操作方向。海洋蓝具体色值、Cybertruck 灵感轮廓和服务站插画由用户反馈与项目设计决定，不是工具输出或学校官方 VI。

V0.5 沿用已确定的海洋蓝布局，仅调整车辆视觉。Car Concept 的模型来源与改编渲染属于素材实施决策，不是 UI/UX Pro Max 生成的模型或图像，也不沿用 V0.4 车形已获用户认可的假设。
