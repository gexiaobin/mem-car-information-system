# 系统更新日志与发布版本

系统在车主页和各角色管理端提供“系统更新日志”入口，展示当前运行版本、各次首次上线时间、标题与功能说明，支持加载更早记录。四种已登录角色均可查看；匿名访问被拒绝。时间在数据库中使用 ISO 时间，界面按 `Asia/Shanghai` 显示。

## 版本如何生成

执行 `npm run build` 时，API 构建脚本 `scripts/build-api.mjs` 读取 `release.config.json`，通过 `scripts/release-manifest.mjs` 计算源码摘要并嵌入编译产物。例如 `0.8.0+0123456789` 由基础版本和 10 位摘要组成，示例摘要不代表某个实际发布。完整摘要生成稳定的 release ID。

摘要覆盖 API、Web 源码与 `index.html` 入口、共享类型、前端公开资产、设计规范、部署／构建脚本及指定的包与配置文件。文本的 CRLF／LF 换行统一后计算，二进制资产按原字节计算，因此同一份源码在 Windows 和 Linux 上保持相同身份。根目录 `docs/` 的说明文档、测试输出、构建产物、`.git`、`.env*`、上传文件及本地数据不参与摘要；仅修改说明文档或重新执行构建不会产生新版本。

Portainer 的 source archive 可以不包含 `.git`：版本身份依据源码内容生成，不依赖 Git 命令、标签或提交消息。能取得 Git 元数据时，附加保存构建时的提交 ID；无 Git 时 `revision=null`，日志功能正常。Git 提交 ID 不替代源码摘要，也不决定当前版本。

正式镜像从 `deploy/Dockerfile.api` 构建时，会复制生成摘要所需的目录和文件。源码包须保留这些内容及 `release.config.json`，不要只上传编译产物后再尝试计算源码版本。运行镜像已包含嵌入的 manifest，无需在容器启动时读取 Git 或重新扫描源码。

## 何时自动记录

1. 构建仅生成版本信息，不写更新日志。
2. API 完成迁移与初始化、成功启动监听后，自动向当前数据库 schema 的 `av_releases` 表登记该构建。
3. 首次登记保存实际启动时间、版本和说明；通过事务及表锁避免并发启动生成重复记录。
4. 标准服务入口等待登记结果。写入失败时停止服务启动，健康检查返回 `RELEASE_RECORD_FAILED`，避免把失败记录静默当作发布成功。

这里的“首次上线”表示 API 构建首次成功启动监听的记录时间，不代表 Web、云端网络、真机或整套业务验收已完成。实际部署及验收仍记录在 [部署说明](deployment.md) 与 [验证记录](verification.md)。不需要新增定时任务、手动 SQL 或环境变量。

`GET /api/v1/releases` 只查询，不补写记录。`GET /api/v1/config`、`GET /api/v1/health` 与 `bootstrap.config.version` 均返回正在运行的构建版本。完整分页和字段见 [API](api.md#系统更新日志)。

## 人工说明与自动摘要

`release.config.json` 格式如下，内容应描述本次实际改动：

```json
{
  "version": "0.8.0",
  "title": "系统更新日志与车型配置目录",
  "changes": [
    "新增系统更新日志，可查看版本、更新时间与功能变更。",
    "发布新版后自动登记更新记录，重复重启不会生成重复日志。"
  ]
}
```

基础版本使用 `主版本.次版本.补丁版本` 的三个非负整数；标题最多保存 120 字符，说明最多 20 条、每条最多 500 字符。构建读取并整理这些字段，系统不会请求 AI 撰写发布记录，也不复制 Git 提交消息。

首次记录在有有效说明时使用当前标题及说明。后续新构建会与最近一次已记录发布比较：

- 标题或说明条目发生变化，且说明非空：使用新维护的功能说明。
- 标题与说明未变：根据发生变化的模块生成中文摘要，例如“车型与参考服务目录更新”“页面展示与交互体验优化”“业务服务与数据校验更新”。不会反复播放上次的人工说明。
- 未提供有效说明且无法得到具体模块变化：使用通用的系统版本更新说明。

模块摘要只说明变更范围，不能代替详细功能文案。需要让用户了解具体行为变化时，应在发布前维护人工说明。只修改基础版本而不更新标题／说明时，采用自动模块摘要。

## 发布者操作步骤

1. 完成代码与公开资源更新，核实配置来源及业务变化。
2. 编辑根目录 `release.config.json`：按本次范围调整基础版本、标题和 `changes`，删除与本次无关的旧说明；保留合法 JSON。
3. 执行 `npm run check`，确认类型检查、测试和构建通过。构建输出会打印嵌入 API 的实际版本。
4. 按 [部署说明](deployment.md) 重新构建并部署 API 与 Web。确保连接原数据库 schema，以保留更新历史。
5. 检查健康接口和容器状态，登录页面打开更新日志，确认当前版本、首次上线时间与说明；随后完成业务验收并记录结果。

本地开发通过 `tsx` 直接启动时，在 API 进程启动阶段读取当前源码快照；源文件改变后应重启 API 才能更新其运行版本。只刷新页面或前端热更新不会改变已运行 API 的版本。

## 重启、回滚与既有历史

相同源码构建重新启动、重新部署或扩容时，已有 release ID 会直接复用，保留原首次上线时间及说明。日志记录为只插入，不会因为重启而改写标题或日期。

回滚到曾运行过的构建时，复用原历史记录；界面按当前运行 manifest 标记该较早版本。历史列表仍按首次上线时间排序，较新的记录不会被删除，列表第一条不一定是当前版本。回滚到一个此前未在该数据库记录过的构建，会在成功启动时首次登记。

启用本功能前的 V0.1–V0.7 不自动补造时间或记录，原验收文档继续保留历史证据。每个数据库 schema 独立维护记录，切换空数据库时仅有在该数据库实际登记过的版本；备份与恢复应包含 `av_releases`。

针对版本摘要、无 Git 源码包、权限、分页、并发幂等、数据库重开和失败健康状态的回归见 `apps/api/tests/releases.test.ts`。真实 PostgreSQL 专项可通过 `AV_RELEASE_PG_TEST=1` 启用，使用随机 `av_test_release_*` schema 并在结束后清理。
