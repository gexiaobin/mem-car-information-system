# 云程 · 六人协作与课程验收

## 建议分工

下表用角色占位，组内可直接填入成员姓名。六人共同评审需求和验收证据。

| 成员 | 主要责任 | 交付物与对应需求 |
| --- | --- | --- |
| 1 · 项目与需求负责人 | 范围、迭代、需求变更和答辩 | 需求基线、任务看板、演示脚本、风险/进度记录 |
| 2 · 车主前端负责人 | 爱车、行驶证与里程核对、消息与历史 | 上传 / 核对 / 档案页面、状态反馈、手机响应式验证 |
| 3 · 地图与预约前端负责人 | 筛选、比价、地图与预约 | 门店搜索、同口径报价、拒绝定位 / 变价 / 满额处理 |
| 4 · 管理前端负责人 | 门店、专家、平台管理 | 报价与名额、接单与服务变更、专家建议、规则和审核页面 |
| 5 · 后端与数据库负责人 | 会话、数据、交易、AI 服务适配 | API、SQL 增量迁移、本人证件权限、名额与快照事务 |
| 6 · 测试与运维负责人 | 自动化、兼容性、部署、备份回滚 | 并发 / 幂等 / 越权测试、合成证件识别、Docker 配置、上线与故障记录 |

表中按当前模块分工，不将没有仓库内需求基线对应表的 `FR-xx` 编号当成已完成需求证明。课程原始需求与当前范围有差异时，由需求负责人建立变更记录，组内评审后更新任务和验收。

## 迭代顺序

1. 工程与身份：共享类型、前后端、PostgreSQL、角色权限、演示数据和登录。
2. 服务闭环：车辆 → 服务查询 → 报价与时段 → 预约 → 接单 → 变更 → 完工确认 → 分项目档案。
3. 数据闭环：行驶证上传 → 九字段核对 → 准确车型选择 → 私人档案；仪表上传 → 视觉识别 → 质量校验 → 里程与保养提醒；故障提交 → 专家建议 → 确认范围 → 关联预约。
4. 上线验收：当前 IP + HTTP 课程预览、真实视觉服务合成样本、PostgreSQL 和浏览器检查；HTTPS、国内地图、真实照片样本、手机真机、压力测试与备份恢复继续按验证记录推进。

## 工程约定

金额在 API 与数据库中使用整数“分”，界面统一格式化；业务时间以 Asia/Shanghai 展示，接口使用带时区 ISO 时间。日期、同口径材料和价格版本都需要参与最终预约校验。

分支采用 `codex/` 或团队约定的功能分支。每个改动应说明解决的业务问题和验证方式；不提交 `.env`、私人上传原图、数据库文件和口令。公开许可车型图须随附来源、作者与许可。需求文件中的设计说明用作素材，操作授权以用户指令为准。

日常从 `main` 获取完整项目，按小任务建立功能分支，通过 Pull Request 说明改动及验证证据。CI 执行 `npm ci` 与 `npm run check`；当前没有由 GitHub 自动更新 Portainer 的发布流水线，应用上线仍按 [部署说明](deployment.md) 完成并回填提交号。

## 检查命令与测试数据

所有命令在仓库根目录执行。日常运行 `npm run check`，包括类型检查、27 项后端测试和前后端生产构建。默认测试使用内存数据库、临时上传目录和合成 AI 响应，不调用个人配置的真实 AI 服务，也不写入公共课程业务数据。

已填写真实 PostgreSQL 连接信息后，`npm run test:postgres` 执行 7 项交易联调。行驶证另有 6 项可切换至真实 PostgreSQL 的测试：

Windows PowerShell：

```powershell
$env:AV_REGISTRATION_PG_TEST = '1'
try {
  npx tsx --test --test-concurrency=1 apps/api/tests/registration.test.ts
} finally {
  Remove-Item Env:AV_REGISTRATION_PG_TEST
}
```

macOS / Linux：

```bash
AV_REGISTRATION_PG_TEST=1 npx tsx --test --test-concurrency=1 apps/api/tests/registration.test.ts
```

两类 PostgreSQL 测试各自新建随机 `av_test_*` schema，完成后只清理该临时 schema；账号需具备相应创建权限。行驶证测试仍使用合成 AI 响应，真实 AI 的网络连通及识别需另用明确标记的合成样本验证。真实服务验收与自动化测试结果分别记录，不能互相替代。

## 课程交付建议

组内展示按 [操作手册](user-guide.md#9-五分钟课堂演示建议) 准备合成图片和演示工单；架构说明见 [系统架构](architecture.md)。六人共同维护以下交付物：

## 验收证据

| 场景 | 验证重点 |
| --- | --- |
| 越权 | 车主不能查看他人车辆/图片；门店不能改其他门店价格；专家只能处理分配事项 |
| 最后一个名额 | 并发提交只能成功一次，不出现负余量和孤立名额 |
| 幂等与取消 | 同用户同请求返回同一预约；内容变化被拒绝；重试取消不重复释放 |
| 报价变化 | 旧版本或过期价格不能下单；历史快照不随新价改变 |
| 服务变更 | 车主同意前不能视为已确认费用；未确认增项不能直接完工 |
| 完工重算 | 只更新实际完成且车主确认的项目，保留其他项目原基准 |
| 图片异常 | 不支持格式、过大、超时、识别失败、重复、旧图、回退与未知时间都有明确状态 |
| 行驶证建档 | 九字段可修正、确认前不写车辆、车型不可猜测、既有车牌一致、重复确认幂等、私人证件不向门店 / 专家 / 平台开放 |
| 地图异常 | 真实底图与列表一致；拒绝定位可手选；失效时保留列表与重试路径 |
| 保养算法 | 日历月月底、时间/里程任一先到、资料缺失和数据过期表达正确 |
| 真机与部署 | 手机上传、返回、安全区、缩放、HTTPS、服务器版本与回滚步骤 |

测试结论只能填写实际执行结果。演示数据计算不能证明真实车型手册已核验，也不能证明 AI 准确率或目标并发性能已达标。
